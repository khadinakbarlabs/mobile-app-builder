# Publisher guide

Run `python3 -m unittest discover -s tests -p 'test_*.py'`, then `python3 tools/release.py`. Source-only dependencies are pinned in requirements-dev.txt. Archives are written to a folder matching the core plugin version, each with a single plugin root and a complete file/hash inventory. They are not placed inside installed folders.

Generate the Codex and Cursor editions with `python3 tools/native_packages.py --output dist/<core-version>`. Each has its own native adapter and inventory. Native directory ZIPs place the manifest at the archive root. The portable edition moves detailed guides to `workflows/` and converts eight commands into compatible skill aliases; the core's 30 public entry IDs remain unchanged. Relative resources and catalog routes are rewritten and checked. Cursor retains native agents and commands. Do not copy an unrelated provider's adapter into a submission archive.

Use Plugin Builder's component budget on the installed core and its validator on the generated Codex package. Validate the exact archive and helper closure as well as the source. Existing host installs must use the supported install flow: update the existing personal marketplace entry and reinstall for Codex; add the local marketplace and qualified plugin for Claude Code; copy the native Cursor package under its supported local plugin folder and reload. Never patch a generated plugin cache. Read back enabled versions and actual component exposure. Keep old copied shortcuts only as scoped compatibility entries that refer to the current full workflow; preserve unrelated skills.

Representative behavior cases and the measured host/fixture evidence belong in publisher-only quality reports. Account/model failures are blocked evaluations, not zero-quality scores or successful comparisons. Do not infer real device behavior, authenticated research or directory approval from the source test suite.

Run the public audit against the repository and both installed roots. Run the supported host CLI version 2.1.287 strict validation against the marketplace and each plugin manifest. Use `node tools/verify-host.mjs plugins/mobile-app-builder` and the optional research folder to compare actual host discovery with the files. Current native skill/agent schema checks are required in addition to manifest checks.

To prepare directory validation, use the public repository with plugin path plugins/mobile-app-builder and tracked branch main. Submit that folder individually after owner review. The optional research folder is a separate plugin and must be validated and behavior-tested independently. Do not select the repository root as the plugin path; that is a marketplace, not a combined installed package.

Do not withdraw the previous submission, accept new legal declarations, configure a secret, or create a replacement directory submission just to run local checks. Owner authorization for a new submission and its declarations remains a distinct external gate. Keep repository, manifest/host checks, live account behavior, directory scan, reviewer clearance and live listing evidence separate.
